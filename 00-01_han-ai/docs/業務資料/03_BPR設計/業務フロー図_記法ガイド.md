# 業務フロー図 記法ガイド ── ざつね屋 実務版

業務の流れを図にするための、最小限のルール集。
BPMN（業務の流れを表す国際的な記法）という標準があるが、中小企業の現場では、
記号を厳密に覚えるより「読める図がすばやく描ける」ことを優先する。

---

## 1. この図で何をしたいのか

業務フロー図は「作ること」が目的ではない。
価値があるのは次の2つ。

- 関係者の認識がそろう（「うちの業務はこう流れている」で合意できる）
- 課題が特定できる（滞留・手戻り・二重作業・属人化が、図の上で見える）

きれいな図の完成に時間をかけるより、下書きを関係者に見せて
「ここ、違う」と言ってもらうほうが、はるかに前に進む。

---

## 2. 使う記号（この6つで足りる）

| 記号 | 意味 | 描き方の目安 |
|---|---|---|
| 角丸四角 | 開始 / 終了 | フローの最初と最後に1つずつ |
| 四角 | 作業（人がやること） | 中に「動詞1つ」で書く |
| ひし形 | 判断・分岐 | 中に判断の問いを書く。線の横に条件を書く |
| 平行四辺形 または 書類マーク | 書類・データ（入力/出力されるもの） | 「受注メモ」「在庫表」など具体名 |
| 四角（左右の辺が二重） | システムが自動でやる処理 | 人の作業と必ず分けて描く |
| 矢印 | 流れの向き | 交差させない。逆流させない |

> 凡例を図の隅に必ず置く。「四角＝作業、ひし形＝分岐」と、その図での約束を明記する。

---

## 3. 7つの基本ルール

1. **記号の意味を、その図の中で統一する** — 上の凡例を図に貼る
2. **時間の向きを一方向にそろえる** — 上から下、または左から右。行ったり来たりさせない
3. **担当ごとに横帯（レーン）で分ける** — 誰の作業かが一目で分かり、部門をまたぐ受け渡しが見える
4. **分岐には必ず条件を書く** — 「はい／いいえ」だけでなく「金額10万円以上／未満」のように判断基準を線の横に
5. **1つの箱は動詞1つ** — 「確認して承認する」は「確認する」「承認する」の2つに分ける
6. **人がやる作業と、システムが自動でやる作業を分けて描く** — どこが手作業として残っているかが読み取れ、そのままAI・自動化の検討材料になる
7. **1枚に詰め込みすぎない** — 目安は1枚30箱まで。超えたら業務を分けて複数枚にする

---

## 4. スイムレーン（担当ごとの横帯）の作り方

```
        ┌──────────────────────────────────────────────┐
 顧客    │  ①注文する ──────────────┐                    │
        ├───────────────────────────┼──────────────────┤
 営業事務│                    ②受注を記録 → ③在庫を確認依頼 │
        ├───────────────────────────┼──────────────────┤
 倉庫    │                          ④在庫を確認 ─┐        │
        ├───────────────────────────┼───────────┼──────┤
 経理    │                                  ⑤請求書を発行 │
        └──────────────────────────────────────────────┘
              時間の向き →（左から右）
```

- レーン（帯）1本 ＝ 1担当（人・役割・部署）
- 帯をまたぐ矢印 ＝ 「受け渡し」。ここに待ち・停滞が起きやすい
- 帯の数が5を超えたら、対象範囲が広すぎる可能性がある

## 5. 作図ツール

| ツール | 向き | 備考 |
|---|---|---|
| draw.io（diagrams.net） | 業務フロー図全般 | 無料。Google Drive に保存できる。スイムレーンの型あり |
| Google 図形描画 / スライド | 簡単な図・共有前提 | クライアントと同時編集しやすい |
| PowerPoint | 提案書に貼る図 | 既存資料と体裁をそろえやすい |
| 手描き（ホワイトボード・紙） | 最初の下書き | 関係者と一緒に描くのが最速。清書は後 |

まずは手描きかホワイトボードで関係者と合意し、清書を draw.io で行うのが定石。

---

## 6. AS-IS（現状）→ TO-BE（あるべき姿）の進め方

1. **AS-IS を描く** — 今どう流れているか。良し悪しの判断はまだしない
2. **AS-IS に課題を書き込む** — 滞留・手戻り・二重作業・属人化の箇所に印をつける
3. **前提を外して TO-BE を描く** — 「今のやり方を前提にしない」。今日ゼロから作るならどうなるか
4. **差分を移行計画にする** — AS-IS と TO-BE の差を、誰が・いつ・何を、の形に落とす（`施策検討シート.xlsx`・移行計画テンプレートへ）

---

## 7. レビュー前チェックリスト

- [ ] 凡例が図の中にある
- [ ] 時間の向きが一方向にそろっている
- [ ] 担当ごとにレーンで分かれている
- [ ] すべての分岐に条件が書いてある
- [ ] 1つの箱が動詞1つになっている
- [ ] 人の作業とシステム処理が分かれている
- [ ] 1枚が30箱以内
- [ ] 開始と終了が1つずつある
- [ ] 関係者に見せて「違う」を出してもらった

## 記入例（テキスト表現）

対象：発注業務／開始点＝発注依頼を受ける／終了点＝発注書を送る

```
[開始] 発注依頼を受ける（担当：営業事務）
  → 在庫を確認する（担当：倉庫）
  → <在庫はあるか？>
       ├ ある → [終了] 発注不要と回答する
       └ ない → 発注数を決める（担当：仕入担当）
              → <発注金額 10万円以上か？>
                   ├ 未満 → 発注書を作成する（担当：仕入担当）
                   └ 以上 → 上長が承認する（担当：部長） → 発注書を作成する
              → 発注書を送る（担当：仕入担当）  [終了]
```
