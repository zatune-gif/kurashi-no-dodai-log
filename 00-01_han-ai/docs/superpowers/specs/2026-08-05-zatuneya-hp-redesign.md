## 4. TOPページ LP構成

### 適用マーケティング理論

- **StoryBrand**: ユーザー中心の物語構造
- **PAS（Problem→Agitate→Solution）**: 問題→扇動→解決
- **Cialdini 互恵性 (Reciprocity)**: 先に価値を提供することで返報性を生起
- **Objection-First**: 悩み・課題提示による不安解消

### セクション順序

1. **ヒーロー** - キャッチコピー＋CTA ×2
2. **悩み・課題提示** - 不安の解消 / Objection-First
3. **無料ツール紹介** - 先にgive → 互恵性 / Reciprocity
4. **なぜざつね屋か** - 信頼構築
5. **サービス概要** - 3本柱サービス紹介
6. **支援の流れ** - プロセス可視化
7. **料金概要** - 価格帯提示
8. **お問い合わせ** - CV（最終CTA）

### 追従要素

**追従スティッキーバナー**
- 常時表示
- 無料診断誘導
- 閉じるボタン付き

## 7. 技術仕様

### JavaScript

- **パターン**: IIFE（即時実行関数式）による独立したモジュール化
- **グローバル変数**: 厳禁
- **ミニマル依存**: バニラJS（フレームワーク・ライブラリ最小化）

### スタイリング

- **インラインstyle**: **禁止**
  - すべてのスタイル定義は `style.css` で管理
  - 動的スタイル変更時は CSS クラス付与で対応
- **グリッド・レイアウト**: Flexbox/CSS Grid 推奨
- **レスポンシブ**: モバイル・タブレット・デスクトップ対応

### ユーザーインタラクション

- **ダイアログ**: `alert()` / `confirm()` / `prompt()` 禁止
  - カスタムモーダル（HTML + CSS + JS）を使用
  - `<dialog>` 要素またはカスタムオーバーレイで実装
- **フォーム検証**: HTML5 validation + 独自フォールバック

### アクセシビリティ

- **ARIA属性**: 意味のないdiv等には適切なrole属性を付与
  - 例：`role="button"` / `role="navigation"` / `role="main"`
- **キーボード操作**: 
  - Tab キーで全対話型要素にアクセス可能
  - Escape キーでダイアログ閉じ対応
  - Enter キーでボタン選択対応
- **言語指定**: `<html lang="ja">` で日本語を明示
- **代替テキスト**: 画像に `alt` 属性、アイコンに `aria-label` を付与

## 8. 品質基準（never skip）

### 基本ルール

1. **「見ただけで判断できるか」** — 初見のユーザーが見た瞬間に意味・目的が分かること
2. **略語禁止** — GA→Google Analytics、バッジには prefix「工程：」等を必ず付ける
3. **インラインstyle禁止** — `innerHTML` 動的生成要素の spacing/sizing は CSS クラス + `!important`
4. **alert/confirm/prompt禁止** — カスタムモーダルを使う
5. **エラー返り値は `{ ok: true, data }` / `{ ok: false, error }` 形式** で統一
6. **著作権表記は `© 2026 ざつね屋`** に統一
7. **外部API連携を実装・改修する前に、必ず最新の公式仕様を確認する**

### LPコンバージョン最適化

1. **CTA文言と遷移先の整合** — ボタン文言と実際の遷移先・フォーム内容を毎回確認
2. **CVセクション配置** — 各セクション内に適切にCVボタンを配置
3. **フォーム最小化** — 初回接点は氏名＋メール＋問い合わせ内容のみ（ハードル最小化）
4. **信頼要素の前置** — 料金提示前に不安要素（よくある質問など）を解消

### 役割分担

| 担当 | 主な役割 |
|---|---|
| Codex | zatuneya-hp の開発・保守・デザイン改善の主担当。通常変更の実装、検証、Git履歴の記録を担う。 |
| Claude Code | 暮らしの土台／ざつね屋事業全体の統括者。事業方針との整合確認、大規模変更の確認、横断的な判断を担う。 |
| ChatGPT | デザイン検討、カンプ作成、全体ディレクションを担う。 |

### ルールファイルの構成

共通ルールの正本は `zatuneya-hp/AGENTS.md` とする。`zatuneya-hp/CLAUDE.md` は Claude Code が作業を始めるための入口として置き、正本の重複は最小限にする。運用ルールはこの最小2ファイル構成で管理する。

### Git運用

- 作業前に必ず `git status` を確認し、他者の未コミット変更を上書き・復元・削除しない。
- 通常変更は、Codex が検証のうえ `main` へ直接反映してよい。
- 事業内容、価格、ブランド、外部ツール接続、公開方式、親構成に関わる大規模変更は、`codex/...` ブランチまたは worktree で行う。Claude Code が差分と検証結果を確認できる状態にしてから統合判断を行う。
- サブモジュールを変更した場合は、サブモジュールで commit・push を先に行い、その後に親リポジトリの gitlink 更新を commit・push する。

### 記録の役割分担

- 設計判断・判断理由は Obsidian に記録する。
- 実装履歴と差分は Git に記録する。
- 繰り返し守る恒久ルールは `AGENTS.md` に記録する。

### 現状リスクと今回の範囲

- `index.html` と `index-v2.html` のどちらを正本とするかが曖昧であり、意図しないページを更新するリスクがある。大規模変更の前に正本と公開経路を明確化する。
- 今回は共同運用設計の追記のみとし、HTML、CSS、JavaScript は変更しない。
- 実装予定のルールファイルは `zatuneya-hp/AGENTS.md` と `zatuneya-hp/CLAUDE.md` のみとする。サイト本体およびその他のファイルは、この設計追記の対象外とする。
